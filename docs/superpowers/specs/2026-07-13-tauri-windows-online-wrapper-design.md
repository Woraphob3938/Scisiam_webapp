# Tauri Windows Online Wrapper Design

## Goal

Package SciSiam as a Windows 10/11 desktop application using Tauri 2 while preserving the deployed Next.js application, Supabase authentication and data access, classroom workflows, and the server-side AI tutor. The first release remains online-first and must not embed any provider, database, or service-role secret.

## Architecture

The desktop application is a thin Tauri shell around `https://scisiam-app.vercel.app`. Vercel remains responsible for Next.js route handlers, middleware, server rendering, authentication callbacks, and `/api/ai-tutor`. Supabase remains the canonical store for sessions and product data.

The Tauri shell owns only desktop concerns:

- Creating and focusing the Windows WebView2 window.
- Restricting top-level navigation to the configured SciSiam origin.
- Opening OAuth and ordinary external URLs in the system browser.
- Receiving the `scisiam://auth/callback` deep link.
- Forwarding a validated OAuth authorization code to the existing web callback.
- Displaying a recoverable connection-failure state.
- Producing a signed-ready Windows installer without including application secrets.

No local Next.js server, bundled Node.js runtime, static export, offline lab database, or direct Gemini integration is included.

## Project Structure

Add Tauri to the existing repository rather than creating a second frontend:

- `src-tauri/Cargo.toml`: Rust dependencies and Windows-only plugin configuration.
- `src-tauri/tauri.conf.json`: application identity, window settings, deep-link scheme, build commands, and NSIS bundle target.
- `src-tauri/src/lib.rs`: window creation, navigation policy, deep-link validation, callback forwarding, and single-instance behavior.
- `src-tauri/src/main.rs`: desktop entry point only.
- `src-tauri/capabilities/default.json`: minimum local capability set. Remote SciSiam content receives no generic filesystem, shell, process, clipboard, or unrestricted opener permission.
- `src-tauri/icons/*`: generated Windows icons derived from the existing SciSiam mascot/brand asset.
- `src/desktop/*`: narrowly scoped browser-side detection and OAuth initiation helpers used by the deployed web application.
- `tests/tauri-desktop.test.mjs`: regression checks for navigation, deep-link, secret, and build configuration.

Add package scripts for desktop development, validation, and Windows bundling without changing the existing web `dev`, `build`, `start`, `lint`, or `test` commands.

## Window And Navigation

The main window uses WebView2 and loads the canonical origin from a compile-time Tauri configuration value. Production defaults to `https://scisiam-app.vercel.app`; development may use `http://localhost:3000` through an explicit development configuration.

Top-level navigation follows these rules:

1. URLs on the exact configured SciSiam origin stay inside the WebView.
2. The Supabase OAuth authorization URL generated by SciSiam opens in the system browser and is not loaded inside WebView2.
3. Other valid `https` URLs open in the system browser.
4. `http`, `file`, `javascript`, `data`, unknown custom schemes, malformed URLs, and unexpected callback hosts are rejected unless required by the explicit development origin.

The Rust layer performs these checks. The remote webpage does not receive a general-purpose native `open URL` command.

## Google OAuth And PKCE

Google authentication uses the system browser because Google does not support embedded user-agent OAuth as a reliable desktop sign-in surface.

Flow:

1. The login page detects the Tauri shell through a narrowly scoped desktop marker.
2. `supabase.auth.signInWithOAuth` runs with Google, `prompt=select_account`, `skipBrowserRedirect=true`, and `redirectTo=scisiam://auth/callback`.
3. The web client assigns the generated Supabase authorization URL as a top-level navigation. Tauri's Rust navigation handler validates the exact Supabase origin and `/auth/v1/authorize` path, cancels the WebView navigation, and opens the URL in the default system browser. This requires no remote IPC capability.
4. Supabase and Google complete authentication in the browser, then redirect to `scisiam://auth/callback?code=<authorization-code>`.
5. Windows launches or focuses the single SciSiam instance. The deep-link plugin passes the URL to Rust.
6. Rust accepts only the exact `scisiam` scheme, `auth` host, `/callback` path, one bounded `code` parameter, and no credential fragments.
7. Rust navigates the existing WebView to `https://scisiam-app.vercel.app/auth/oauth-callback?code=<encoded-code>&next=/profile`.
8. The existing callback exchanges the code for a Supabase session using the PKCE verifier retained in the WebView cookie/storage context.
9. The authenticated WebView continues to `/profile`; role-aware web navigation remains unchanged.

The single-instance plugin must initialize before the deep-link plugin. Development registration is allowed only for the `scisiam` scheme. Supabase Auth must list `scisiam://auth/callback` as an Additional Redirect URL while keeping the HTTPS site URL canonical.

## Security Boundary

- No `GEMINI_API_KEY`, Supabase service-role key, database password, access token, refresh token, or environment file is bundled.
- The application uses only the same public Supabase URL and publishable key already exposed to the web client.
- Remote content does not receive filesystem, shell, process, unrestricted opener, or arbitrary Tauri command access.
- OAuth URLs are checked against the configured Supabase origin and expected authorization path before opening.
- Deep links are treated as untrusted input and validated before use.
- Authorization codes are never logged and are removed from the visible address after the existing callback completes.
- PKCE is required; implicit-flow access and refresh tokens are not accepted from the deep-link URL.
- Existing Supabase RLS and guarded classroom RPC authorization remain the authority for product data.

## Connection Failure Experience

At startup the shell first presents a local branded loading surface while checking the configured SciSiam origin. A successful check opens the remote application. A timeout, DNS failure, TLS failure, or offline state shows a local Thai error surface with:

- A clear offline/connection message.
- A `ลองใหม่` action.
- A `เปิดในเบราว์เซอร์` fallback.
- No stale authenticated data or cached classroom content.

If connectivity fails after the remote application has loaded, normal web request error handling remains active. A later release may add a richer offline lab mode.

## Windows Packaging

- Target Windows 10/11 x64 first.
- Require Rust stable MSVC, Microsoft C++ Build Tools with Desktop development for C++, and Edge WebView2 Runtime.
- Produce an NSIS `.exe` installer in the first release.
- Use a stable reverse-DNS application identifier and register the `scisiam` URL scheme during installation.
- Keep versioning aligned between `package.json`, `Cargo.toml`, and `tauri.conf.json`.
- Configure a publisher and code-signing certificate through CI or protected local environment variables when available; unsigned development installers must be labeled as such.
- MSI packaging is deferred until the Windows VBSCRIPT/WiX prerequisites and signing pipeline are verified.

## Web Application Changes

The existing web application remains fully usable in ordinary browsers. Desktop-specific behavior is activated only when the Tauri shell marker is present.

- Email/password sign-in remains unchanged.
- Google sign-in chooses browser OAuth only in Tauri; ordinary web OAuth keeps the current HTTPS callback.
- Auth errors return the login page to an actionable state instead of leaving the Google button loading.
- The desktop callback reuses `/auth/oauth-callback`; no second session implementation is introduced.
- External links behave normally in browsers and are routed to the system browser by the Tauri navigation policy.

## Testing

Automated checks must cover:

- Tauri configuration uses the expected production origin, Windows identifier, NSIS target, and `scisiam` scheme.
- No secret names or secret values appear in Rust source, Tauri configuration, capabilities, or bundled frontend configuration.
- The navigation policy allows only the configured SciSiam origin in-app.
- Supabase OAuth authorization opens externally only after origin/path validation.
- Deep-link validation accepts one well-formed callback and rejects wrong schemes, hosts, paths, missing codes, duplicate codes, fragments, and oversized codes.
- A callback focuses the existing window and forwards an encoded code to the existing HTTPS callback.
- Tauri Google login uses `skipBrowserRedirect`, the custom callback, and account selection; normal browser Google login remains unchanged.
- Email login remains unchanged.
- The local connection screen supports retry and browser fallback.
- Existing `npm test`, `npm run lint`, and `npm run build` continue to pass.
- `cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test`, `npm run tauri build -- --bundles nsis`, secret scan, and manual installed-app OAuth QA pass before release.

Manual Windows QA must test cold-start OAuth, OAuth while the app is already open, canceling Google login, invalid/expired callback codes, offline startup, reconnection, file upload, experiment snapshots, classroom submissions, AI tutor, and installer uninstall/reinstall behavior.

## Failure Handling

- Missing Tauri prerequisites: fail the desktop build with installation guidance; web development remains available.
- System browser cannot open: show a Thai error and reset OAuth loading state.
- User cancels OAuth: keep the login form usable and provide retry.
- Invalid deep link: ignore it, focus the app, and show no credentials or technical payload.
- Expired/reused code: existing callback returns the branded login error flow.
- Callback arrives before the window is ready: queue one validated callback and process it after window creation.
- A second app launch: focus the first instance and forward only a validated deep link.
- Remote origin unavailable: keep the local retry surface available.

## Deployment And Operations

Before distributing the installer:

1. Add `scisiam://auth/callback` to Supabase Additional Redirect URLs.
2. Keep `NEXT_PUBLIC_SITE_URL=https://scisiam-app.vercel.app` and the HTTPS site URL canonical.
3. Verify Google provider settings and consent configuration remain valid for the Supabase callback domain.
4. Build from a clean commit with no `.env.local` or generated installer output staged.
5. Store signing credentials outside Git and outside the application bundle.
6. Publish the installer checksum and version alongside the download.

## Out Of Scope

- Offline simulations, offline authentication, or local classroom data.
- Bundling a Next.js or Node.js server inside Tauri.
- Static export of the current application.
- Auto-update infrastructure.
- macOS, Linux, Android, or iOS packages.
- MSI packaging in the first release.
- Native filesystem integration beyond the WebView's existing browser file picker.
- Background services, system tray behavior, notifications, or launch-at-startup.
