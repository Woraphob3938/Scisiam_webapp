# SciSiam NSC 2026 Software Disclaimer Design

**วันที่:** 17 กรกฎาคม 2569
**สถานะ:** อนุมัติแนวทางแล้ว รอผู้ใช้ตรวจสเปกฉบับเขียน

## 1. เป้าหมาย

เพิ่ม “ข้อตกลงในการใช้ซอฟต์แวร์” ตามข้อกำหนดของการแข่งขันพัฒนาโปรแกรมคอมพิวเตอร์แห่งประเทศไทย ครั้งที่ 28 (NSC 2026) ลงในแอป SciSiam โดยทำให้กรรมการและผู้ใช้เห็นข้อความได้ชัดเจนตั้งแต่การเปิดหน้าเข้าสู่ระบบหรือสมัครสมาชิกครั้งแรก และสามารถกลับมาเปิดอ่านซ้ำได้ตลอดเวลา

การเปลี่ยนแปลงนี้เป็นการแสดงข้อความประกาศ ไม่ใช่ระบบบันทึกความยินยอมทางกฎหมาย และต้องไม่ขัดขวางการเข้าสู่ระบบหรือสมัครสมาชิก

## 2. ข้อมูลที่ใช้ในข้อตกลง

### ชื่อผลงาน

**ไซสยาม: ห้องทดลองวิทยาศาสตร์ออนไลน์ เพื่อการศึกษาไทยที่ยั่งยืนทั่วทุกพื้นที่**
ชื่อผลิตภัณฑ์ที่ใช้ในแอป: **SciSiam Simulation Lab**

### คณะผู้พัฒนา

1. นางสาวชัชนัน บุญเหลือง
2. นายวรภพ ไชยวงศ์คต
3. นายพิพัฒน์ โพธิ์ศรีสุข

### อาจารย์ที่ปรึกษา

ผู้ช่วยศาสตราจารย์ ดร.ทวี งามวิไลกร

### สถาบัน

คณะวิทยาศาสตร์และวิศวกรรมศาสตร์ มหาวิทยาลัยเกษตรศาสตร์ วิทยาเขตเฉลิมพระเกียรติ จังหวัดสกลนคร

### ชื่อโครงการสนับสนุน

โครงการการแข่งขันพัฒนาโปรแกรมคอมพิวเตอร์แห่งประเทศไทย ครั้งที่ 28

ชื่อผลงานและชื่อโครงการสนับสนุนต้องเป็นคนละช่องข้อมูล เพื่อไม่ให้ข้อความ “ภายใต้โครงการ” ถูกกรอกด้วยชื่อผลิตภัณฑ์แทนชื่อโครงการของ NSC

## 3. ข้อความประกาศฉบับใช้งาน

> ซอฟต์แวร์นี้เป็นผลงานที่พัฒนาขึ้นโดย นางสาวชัชนัน บุญเหลือง นายวรภพ ไชยวงศ์คต และนายพิพัฒน์ โพธิ์ศรีสุข จากคณะวิทยาศาสตร์และวิศวกรรมศาสตร์ มหาวิทยาลัยเกษตรศาสตร์ วิทยาเขตเฉลิมพระเกียรติ จังหวัดสกลนคร ภายใต้การดูแลของผู้ช่วยศาสตราจารย์ ดร.ทวี งามวิไลกร ภายใต้โครงการการแข่งขันพัฒนาโปรแกรมคอมพิวเตอร์แห่งประเทศไทย ครั้งที่ 28 ซึ่งสนับสนุนโดย สำนักงานพัฒนาวิทยาศาสตร์และเทคโนโลยีแห่งชาติ โดยมีวัตถุประสงค์เพื่อส่งเสริมให้นักเรียนและนักศึกษาได้เรียนรู้และฝึกทักษะในการพัฒนาซอฟต์แวร์ ลิขสิทธิ์ของซอฟต์แวร์นี้จึงเป็นของผู้พัฒนา ซึ่งผู้พัฒนาได้อนุญาตให้สำนักงานพัฒนาวิทยาศาสตร์และเทคโนโลยีแห่งชาติเผยแพร่ซอฟต์แวร์นี้ตาม “ต้นฉบับ” โดยไม่มีการแก้ไขดัดแปลงใด ๆ ทั้งสิ้น ให้แก่บุคคลทั่วไปได้ใช้เพื่อประโยชน์ส่วนบุคคลหรือประโยชน์ทางการศึกษาที่ไม่มีวัตถุประสงค์ในเชิงพาณิชย์ โดยไม่คิดค่าตอบแทนการใช้ซอฟต์แวร์ ดังนั้น สำนักงานพัฒนาวิทยาศาสตร์และเทคโนโลยีแห่งชาติ จึงไม่มีหน้าที่ในการดูแล บำรุงรักษา จัดการอบรมการใช้งาน หรือพัฒนาประสิทธิภาพซอฟต์แวร์ รวมทั้งไม่รับรองความถูกต้องหรือประสิทธิภาพการทำงานของซอฟต์แวร์ ตลอดจนไม่รับประกันความเสียหายต่าง ๆ อันเกิดจากการใช้ซอฟต์แวร์นี้ทั้งสิ้น

ข้อความข้างต้นใช้ภาษาไทยตามต้นฉบับข้อกำหนดที่ผู้ใช้ให้มา โดยแทนค่าชื่อทั้งหมดแล้ว และต้องเก็บเป็นข้อความจริงในหน้าเว็บ ไม่ทำเป็นรูปภาพ

## 4. ประสบการณ์ผู้ใช้

### การเปิดอัตโนมัติ

- หน้า `/login` และ `/register` ตรวจสถานะหลังฝั่งไคลเอนต์ทำงานแล้ว เพื่อหลีกเลี่ยง hydration mismatch
- หากไม่พบคีย์ `scisiam_nsc_disclaimer_seen_v1` ให้เปิดหน้าต่างข้อตกลงอัตโนมัติ
- เมื่อผู้ใช้ปิดหน้าต่างด้วยปุ่ม “รับทราบและดำเนินการต่อ” ปุ่มปิด หรือปุ่ม Escape ให้บันทึกคีย์ดังกล่าวใน `localStorage`
- หากอ่านหรือเขียน `localStorage` ไม่ได้ แอปยังทำงานต่อได้ และผู้ใช้ยังเปิดข้อความผ่านลิงก์ถาวรได้
- คีย์มีเลขเวอร์ชันเพื่อให้สามารถแสดงข้อความฉบับใหม่อีกครั้งในอนาคตโดยไม่กระทบข้อมูลอื่น

### การเปิดอ่านซ้ำ

- ใต้แบบฟอร์มเข้าสู่ระบบและสมัครสมาชิกมีปุ่มข้อความแบบลิงก์ชื่อ “ข้อตกลงการใช้ซอฟต์แวร์ NSC 2026”
- ในหน้าต่างตั้งค่ามีรายการ “ข้อตกลงการใช้ซอฟต์แวร์ NSC 2026”
- เมื่อเปิดจากหน้าต่างตั้งค่า ให้ปิดหน้าต่างตั้งค่าก่อน แล้วเปิดหน้าต่างข้อตกลง เพื่อไม่สร้าง modal ซ้อน modal
- การเปิดด้วยลิงก์ถาวรทำได้เสมอ ไม่ขึ้นกับสถานะ `seen`

### ความสัมพันธ์กับแบบฟอร์มสมัครสมาชิก

- ไม่เปลี่ยนความหมายหรือกลไกของช่องยอมรับเงื่อนไขการใช้งานและนโยบายความเป็นส่วนตัวที่มีอยู่
- ข้อตกลง NSC เป็นข้อความประกาศแยกต่างหาก ไม่ใช้แทนนโยบายความเป็นส่วนตัวและไม่เพิ่มการบันทึก consent ในฐานข้อมูล

## 5. รูปแบบหน้าต่าง

- ใช้สไตล์ SciSiam สีขาว–ฟ้า เรียบ เป็นทางการ และมีป้าย “NSC 2026”
- หัวข้อหลักคือ “ข้อตกลงในการใช้ซอฟต์แวร์”
- ส่วนต้นแสดงชื่อผลงาน ชื่อคณะผู้พัฒนา สถาบัน และอาจารย์ที่ปรึกษาในกรอบสรุป
- ส่วนถัดไปแสดงข้อความประกาศฉบับเต็มด้วยตัวอักษรสีดำหรือสีเทาเข้มบนพื้นขาว
- ส่วนหัวและส่วนปุ่มด้านล่างอยู่คงที่ ส่วนข้อความตรงกลางเลื่อนได้
- ความกว้างสูงสุดเหมาะกับเดสก์ท็อป และย่อเหลือหนึ่งคอลัมน์โดยไม่เกิดการเลื่อนแนวนอนที่ความกว้าง 390px และ 320px
- ปุ่มหลักใช้ข้อความ “รับทราบและดำเนินการต่อ” และมีปุ่มปิดที่มองเห็นได้บริเวณมุมขวาบน
- ลิงก์ในเนื้อความต้องมีเส้นใต้หรือสัญลักษณ์ที่ไม่ได้พึ่งสีเพียงอย่างเดียว

## 6. โครงสร้างโค้ด

### ข้อมูลกลาง

สร้างไฟล์ข้อมูลกลางสำหรับ:

- ชื่อผลงานและชื่อผลิตภัณฑ์
- รายชื่อผู้พัฒนา
- ชื่ออาจารย์ที่ปรึกษา
- ชื่อสถาบัน
- ชื่อโครงการสนับสนุน
- ข้อความประกาศฉบับเต็ม
- คีย์ `localStorage`

คอมโพเนนต์ทุกจุดต้องอ่านข้อมูลจากแหล่งเดียวกัน เพื่อไม่ให้การสะกดหรือข้อความต่างกัน

### คอมโพเนนต์หน้าต่าง

สร้าง `SoftwareDisclaimerDialog` เป็น client component แบบควบคุมด้วย `open` และ `onOpenChange` เพื่อให้ใช้ร่วมกันได้ทั้งหน้า Auth และ Navbar

โครงการมี Radix/shadcn Dialog primitive ใช้อยู่แล้ว จึงใช้ primitive เดิมแทนการสร้างกลไก modal ใหม่ แม้ native `<dialog>` จะเป็นตัวเลือกเชิง semantics ที่ตรงไปตรงมา การใช้ primitive เดิมเป็นข้อจำกัดทางเทคนิคที่สมเหตุผลเพราะมี focus trap, Escape handling, portal และ focus return ที่ผ่านการใช้ร่วมกับส่วนอื่นของแอปอยู่แล้ว

### จุดเชื่อมต่อ

- `AuthForm` เป็นเจ้าของสถานะเปิดอัตโนมัติและปุ่มเปิดอ่านซ้ำในหน้า Login/Register
- `Navbar` เป็นเจ้าของสถานะระหว่าง Settings และ Disclaimer เพื่อรับประกันว่าเปิดได้ครั้งละหนึ่งหน้าต่าง
- `SettingsModal` รับ callback สำหรับคำสั่งเปิดข้อตกลง โดยไม่สร้างหน้าต่างซ้อนภายในตัวเอง

## 7. การเข้าถึง

การออกแบบต้องผ่านแนวทางจาก accessibility lead, modal, ARIA, keyboard, contrast, heading และ form ดังนี้:

- ใช้ Dialog semantics ของ primitive พร้อม `aria-modal` และชื่อหน้าต่างที่อ้างถึงหัวข้อ
- ใช้หัวข้อระดับ `h2` ภายใน modal และหัวข้อย่อยตามลำดับโดยไม่ข้ามระดับ
- ไม่ใช้ `aria-describedby` ครอบข้อความยาวทั้งฉบับ เพราะจะทำให้โครงสร้างย่อหน้าและรายการถูกอ่านเป็นสตริงเดียว
- เมื่อเปิดข้อความยาว ให้โฟกัสหัวข้อที่มี `tabIndex={-1}` เพื่อให้โปรแกรมอ่านหน้าจอเริ่มอ่านจากจุดที่ถูกต้อง
- Tab และ Shift+Tab ต้องอยู่ภายใน modal ขณะเปิด และ Escape ต้องปิดได้
- เมื่อปิด ต้องคืนโฟกัสไปยังปุ่มที่ใช้เปิด หากเป็นการเปิดอัตโนมัติให้คืนโฟกัสไปยังตำแหน่งที่เหมาะสมในแบบฟอร์ม
- พื้นที่ข้อความที่เลื่อนได้ต้องเข้าถึงและเลื่อนด้วยแป้นพิมพ์ได้
- ปุ่มเปิดทุกจุดใช้ `<button type="button">` และมี `aria-haspopup="dialog"`
- ไอคอนที่มีข้อความกำกับต้องใช้ `aria-hidden="true"`; ปุ่มไอคอนปิดต้องมี accessible name
- ตัวอักษรเนื้อหาขนาดอย่างน้อย 16px พร้อม `line-height` อย่างน้อย 1.6 สำหรับภาษาไทย
- ข้อความปกติต้องมี contrast อย่างน้อย 4.5:1, ขอบ/ปุ่ม/วงแหวนโฟกัสอย่างน้อย 3:1 และเป้าหมายการกดอย่างน้อย 44×44px เมื่อทำได้
- รองรับ `prefers-reduced-motion`, `prefers-contrast` และ `forced-colors` ตามรูปแบบส่วนกลางของโครงการ
- ไม่แก้โครงสร้างหรือ validation ของ checkbox สมัครสมาชิกโดยไม่จำเป็น

## 8. การจัดการข้อผิดพลาด

- ห่อการอ่านและเขียน `localStorage` ด้วย `try/catch`
- ความล้มเหลวของ `localStorage` ต้องไม่ทำให้หน้า Auth ล้ม ไม่ทำให้ปุ่ม Login/Register ใช้ไม่ได้ และไม่สร้างข้อความ error ที่รบกวนผู้ใช้
- ข้อมูลประกาศเป็น static content จึงไม่มี loading state หรือ network request
- หาก callback จาก Settings ถูกเรียก ให้ปิด Settings ก่อนและเปิด Disclaimer ใน event loop ถัดไปหากจำเป็น เพื่อให้การคืนโฟกัสไม่ชนกัน

## 9. การทดสอบ

### TDD และ regression tests

สร้างการทดสอบก่อนแก้โค้ด โดยตรวจอย่างน้อย:

1. ไฟล์ข้อมูลมีชื่อผู้พัฒนาทั้งสามคน ชื่ออาจารย์ สถาบัน ชื่อผลงาน และชื่อโครงการสนับสนุนตรงตามสเปก
2. ข้อความประกาศมีข้อความสำคัญเรื่องเจ้าของลิขสิทธิ์ การเผยแพร่ตาม “ต้นฉบับ” การใช้แบบไม่แสวงหากำไร และการไม่รับประกันความเสียหาย
3. `SoftwareDisclaimerDialog` มีหัวข้อ ปุ่มปิด ปุ่มรับทราบ โครงสร้างข้อความ และการเปิด/ปิดแบบ controlled
4. `AuthForm` ตรวจคีย์ `scisiam_nsc_disclaimer_seen_v1`, เปิดครั้งแรก และมีปุ่มเปิดอ่านซ้ำ
5. `SettingsModal` และ `Navbar` เปิดข้อตกลงโดยไม่เกิด modal ซ้อนกัน
6. ไม่มีการเพิ่ม database write หรือ API request สำหรับสถานะ `seen`

### คำสั่งตรวจ

- `npm test`
- `npm run lint`
- `npm run build`

### Browser QA

ตรวจ `/login` และ `/register` อย่างน้อยในกรณีต่อไปนี้:

- เดสก์ท็อปและมือถือกว้าง 390px
- reflow ที่ความกว้าง 320px
- เปิดครั้งแรกและกลับมาเปิดครั้งถัดไป
- เปิดอ่านซ้ำจาก Auth และ Settings
- Tab, Shift+Tab, Escape, focus trap และ focus return
- การเลื่อนอ่านข้อความยาวด้วยแป้นพิมพ์
- ไม่มี horizontal overflow, console error หรือ hydration warning
- การเข้าสู่ระบบ สมัครสมาชิก และ Google OAuth ยังทำงานเหมือนเดิม

## 10. ขอบเขตที่ไม่ทำในงานนี้

- ไม่สร้างระบบบันทึก consent ใน Supabase
- ไม่สร้างหรือแก้ไขนโยบายความเป็นส่วนตัว
- ไม่เพิ่มข้อความภาษาอังกฤษ เพราะกติกาอนุญาตภาษาไทยหรือภาษาอังกฤษ และผู้ใช้ให้ต้นฉบับภาษาไทย
- ไม่เพิ่มโลโก้ NSC/NSTDA ที่ยังไม่มีสิทธิ์หรือไฟล์ต้นฉบับในโครงการ
- ไม่เปลี่ยนเส้นทางหลังเข้าสู่ระบบ
- ไม่แก้หน้าทดลอง ห้องเรียน โปรไฟล์ หรือระบบ AI นอกเหนือจากปุ่มเปิดอ่านในเมนูตั้งค่า

## 11. เกณฑ์ยอมรับงาน

งานถือว่าสำเร็จเมื่อ:

- กรรมการพบข้อตกลงทันทีเมื่อเปิด Login/Register ครั้งแรก
- ข้อความและชื่อทุกส่วนตรงตามสเปกโดยไม่มี placeholder
- ผู้ใช้เปิดอ่านซ้ำได้จากหน้า Auth และ Settings
- modal ใช้คีย์บอร์ดและโปรแกรมอ่านหน้าจอได้ตามข้อกำหนด
- หน้า Login/Register ไม่เสียพฤติกรรมเดิม
- test, lint และ build ผ่าน
- Browser QA ที่ 390px และ 320px ไม่พบ overflow หรือจุดใช้งานที่ถูกบัง
